## 3. Audited Findings Ranked by Severity

### [CRITICAL-01] Arbitrary Client `storageKey` Acceptance & Object Hijacking
- **File Reference:** `src/app/api/store/quotes/route.ts` (Lines 117–138), `src/lib/storefront.ts` (Lines 231–233).
- **Vulnerability Description:**
  In `POST /api/store/quotes`, the endpoint accepts `storageKey`, `fileName`, and `fileSizeBytes` directly from the client JSON payload:
  ```ts
  if (data.storageKey && data.fileName && data.fileSizeBytes) {
    await sql`
      INSERT INTO public.store_quote_files (
        quote_request_id, file_name, file_size_bytes, mime_type, file_extension, storage_key
      ) VALUES (
        ${quoteRequestId}, ${data.fileName}, ${data.fileSizeBytes},
        'application/octet-stream', ${ext}, ${data.storageKey}
      );
    `;
  }
  ```
  The endpoint performs zero validation that:
  1. The `storageKey` was actually generated by the server via `/api/store/quotes/presign`.
  2. The `storageKey` was issued to the requesting client / IP address.
  3. The object actually exists in Cloudflare R2 (e.g. via an S3 `HeadObject` call).
  4. The `storageKey` belongs to an unassigned quote rather than another customer's confidential CAD file.
- **Exploit Scenario:**
  An attacker can submit an RFQ associating another customer's confidential intellectual property (`uploads/rfq/1794989478_victim_prototype.step`) with their own quote request, or submit fictitious file metadata for an object that was never uploaded.
- **Required Remediation:**
  1. Introduce a server-signed upload token (HMAC-SHA256 signature containing `storageKey`, `fileSizeBytes`, `clientIp`, `issuedAt`, `expiresAt`) issued during `/presign` that must be presented to `/api/store/quotes`.
  2. Alternatively, persist pending upload intents in a database table (`store_upload_intents`) and enforce that a quote can only bind an unconsumed, non-expired intent issued to the same client IP.
  3. Perform a server-side `HeadObject` check (when R2 is configured) before inserting into `store_quote_files`.

### [HIGH-01] Presigned PUT URL Lacks Content-Type & Content-Length Bounds
- **File Reference:** `src/lib/r2.ts` (Lines 80–108), `src/app/api/store/quotes/presign/route.ts` (Lines 89–98).
- **Vulnerability Description:**
  The AWS SigV4 signer in `generatePresignedPutUrl()` signs only the `host` header (`X-Amz-SignedHeaders=host`). It does **not** include `content-type` or `content-length` in the canonical request headers.
- **Risk Impact:**
  1. **Unbounded Upload Size:** Even though `/presign` validates `fileSizeBytes <= 50 MB` on the JSON request, the S3/R2 presigned PUT URL itself does not enforce this restriction. An attacker can use the presigned URL to upload a 5 GB file directly to R2, bypassing the 50 MB limit and incurring storage exhaustion / egress costs.
  2. **MIME Type Masquerading:** The client can upload arbitrary executable or HTML content with `Content-Type: text/html` under a `.step` extension.
- **Required Remediation:**
  Include `content-type` in `X-Amz-SignedHeaders` or configure Cloudflare R2 bucket-level max object size limits / presigned POST policies with strict `['content-length-range', 1, 52428800]`.

### [HIGH-02] Non-Transactional Multi-Query Insert in Custom Quote API
- **File Reference:** `src/app/api/store/quotes/route.ts` (Lines 79–138).
- **Vulnerability Description:**
  `POST /api/store/quotes` executes two separate database calls via `sql` (Neon HTTP serverless client):
  ```ts
  // Query 1: Inserts quote header
  const requestResult = await sql`INSERT INTO public.store_quote_requests (...) RETURNING id;`;
  
  // Query 2: Inserts child file attachment
  if (data.storageKey && ...) {
    await sql`INSERT INTO public.store_quote_files (...) VALUES (...);`;
  }
  ```
  Because Neon HTTP query calls execute as independent auto-commit transactions, if Query 2 fails (due to a transient network timeout, storage key length violation, or database error), Query 1 has already committed.
- **Risk Impact:**
  Orphaned quote requests in `store_quote_requests` with missing CAD file attachments, causing factory operators to receive incomplete RFQs without the required models.
- **Required Remediation:**
  Wrap multi-table operations in a transaction block using Neon's `sql.transaction([...])` or a single CTE:
  ```sql
  WITH new_quote AS (
    INSERT INTO public.store_quote_requests (...) VALUES (...) RETURNING id
  )
  INSERT INTO public.store_quote_files (quote_request_id, ...)
  SELECT id, ... FROM new_quote;
  ```

### [HIGH-03] Missing Origin / CSRF Enforcement on Public Storefront Mutation Endpoints
- **File Reference:** `src/app/api/store/enquiries/route.ts`, `src/app/api/store/quotes/presign/route.ts`, `src/app/api/store/quotes/route.ts`.
- **Vulnerability Description:**
  `PHASE_2_ROUTE_MAP.md` (lines 59–61) explicitly specifies `CSRF Check: Origin Header` for `/api/store/enquiries`, `/quotes/presign`, and `/quotes`.
  However, none of these route handlers invoke `validateOrigin(req)` or verify that the incoming `Origin` / `Referer` matches the allowed storefront hostname (`www.lvh.me` or `process.env.STORE_HOSTNAME`).
- **Risk Impact:**
  Malicious third-party websites can trigger cross-origin POST requests from legitimate users' browsers, creating spam quote requests or consuming the user's IP rate-limit budget without their knowledge.
- **Required Remediation:**
  Enforce origin validation for storefront POST requests:
  ```ts
  const origin = req.headers.get('origin');
  if (origin && !isAllowedStorefrontOrigin(origin)) {
    return NextResponse.json({ error: 'INVALID_ORIGIN' }, { status: 403 });
  }
  ```

### [MEDIUM-01] Incomplete URL Scheme Sanitization in `sanitizeProductForStorefront()`
- **File Reference:** `src/lib/storefront.ts` (Lines 58–70).
- **Vulnerability Description:**
  In `sanitizeProductForStorefront()`, when handling `data.photo`, the code strictly requires `http://` or `https://`:
  ```ts
  } else if (typeof data.photo === 'string' && data.photo.trim().length > 0) {
    const trimmed = data.photo.trim();
    if (trimmed.startsWith('http://') || trimmed.startsWith('https://')) {
      imageUrl = trimmed;
    }
  }
  ```
  However, when handling `data.imageUrl`, it only checks:
  ```ts
  if (typeof data.imageUrl === 'string' && data.imageUrl.trim().length > 0) {
    const trimmed = data.imageUrl.trim();
    if (!trimmed.startsWith('data:image/')) {
      imageUrl = trimmed;
    }
  }
  ```
- **Risk Impact:**
  If an administrator or database record contains `data.imageUrl = "javascript:alert(1)"` or `data:text/html,...`, it passes through unredacted to the public client.
- **Required Remediation:**
  Enforce the same scheme check on `data.imageUrl`:
  `if (/^(https?:\/\/|\/)/i.test(trimmed)) { imageUrl = trimmed; }`

### [MEDIUM-02] Migration Statement Parser Skips Comment-Prefixed Blocks
- **File Reference:** `scripts/migrate.ts` (Lines 96–99).
- **Vulnerability Description:**
  The migration runner splits SQL scripts using:
  `content.split(/;\s*[\r\n]+/).map(s => s.trim()).filter(s => s.length > 0 && !s.startsWith('--'))`
  If a statement begins with a SQL comment line (e.g. `-- 1. Table definition\nCREATE TABLE ...`), `s.startsWith('--')` evaluates to `true` for the entire multi-line string, causing the migration runner to completely omit the statement.
- **Risk Impact:**
  Future migrations with comments before SQL statements will fail or be silently omitted.
- **Required Remediation:**
  Strip SQL comment lines before statement evaluation:
  ```ts
  const cleanSql = content.replace(/--.*$/gm, '');
  const statements = cleanSql.split(';').map(s => s.trim()).filter(Boolean);
  ```

### [LOW-01] Non-Gapless Sequence Numbering Claim
- **File Reference:** `src/app/api/store/quotes/route.ts` (Lines 74–77), `migrations/0002_phase2_storefront_foundation.sql` (Line 1).
- **Observation:**
  `store_rfq_seq` is a standard PostgreSQL sequence. In PostgreSQL, sequences increment monotonically but are **not gapless** (failed transactions or crashes permanently consume sequence numbers).
- **Assessment:**
  This is standard and acceptable for quote reference IDs (`RFQ-2026-1001`), but documentation and audit reports must not claim gapless guarantees.

## 7. Mandatory Action Items Before Phase 2.5

The following items must be resolved in Phase 2.4.1 (or at the start of Phase 2.5) before launching the storefront UI:

1. **Upload Intent Tokenization:**
   Issue an HMAC-SHA256 signed `uploadToken` from `/api/store/quotes/presign` encoding `{ storageKey, fileSizeBytes, clientIp, exp }`. Require this token in `POST /api/store/quotes` to prevent arbitrary storage key association.
2. **Transactional RFQ Insertion:**
   Refactor `POST /api/store/quotes` to wrap the quote request and quote file insertions into a single database transaction.
3. **Storefront Origin Validation:**
   Add `validateOrigin(req)` or strict allowed-origin checking on `/api/store/enquiries`, `/quotes/presign`, and `/quotes`.
4. **Image URL Scheme Whitelisting:**
   Update `sanitizeProductForStorefront()` to require `http://`, `https://`, or `/` on `data.imageUrl`.
5. **Migration Statement Parser Fix:**
   Update `scripts/migrate.ts` to strip comments before splitting on `;`.
